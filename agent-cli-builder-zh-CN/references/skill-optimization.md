# 生产级 Skill 优化指南（中文）

> 本指南供 AI agent 使用。目标不是“把文档写得更漂亮”，而是把现有 skill 优化成可信、稳定、精准、可维护且真正解决任务的生产资产。

## 1. 最终标准

生产可用的 skill 必须同时满足 TRACE 五个维度:

| 维度          | 必须解决的问题         | 生产标准                                                         |
| ------------- | ---------------------- | ---------------------------------------------------------------- |
| Trust         | 能不能放心用           | 无隐蔽副作用，不泄露敏感信息，不夸大能力，依赖和网络边界透明     |
| Reliability   | 能不能稳定用           | 正常、边界和失败输入均有确定行为；字段、命令和恢复流程与实现一致 |
| Adaptability  | 该不该在这个场景用     | 触发条件、排除条件和相邻 skill 边界明确                          |
| Convention    | 能不能理解、维护和复用 | 信息分层清晰，机械内容自动生成，语义内容精简且可验证             |
| Effectiveness | 是否真正解决了问题     | 输出正确、完整、可直接使用，并提供有证据的整合或判断             |

将 Trust 和 Reliability 视为硬门槛。任一不通过，不得宣称生产可用。不要用漂亮输出掩盖安全风险或错误结果。

## 2. 好 Skill 与坏 Skill

### 好 Skill

- `description` 写明用户何时会用、主要说法和最容易混淆的排除边界。
- 正文以祈使句给出可执行步骤，不解释 agent 已经知道的常识。
- 调用前检查真实依赖；缺少依赖时说明影响并提供安装指引，不静默修改环境。
- 命令、参数、默认值、字段和返回结构均以代码或真实输出为依据。
- 对敏感输入、远程传输、写操作和高风险结论设置明确边界。
- 对部分失败、空结果、过期数据和字段缺失定义降级行为。
- 将命令签名等机械信息交给生成器，将复杂字段和变体放入 `references/`。
- 输出与用户目标一致，而不只是“成功调用了工具”。
- 通过静态校验、构建、测试、打包检查和真实任务前向评测。

### 坏 Skill

- `description` 只写“办公助手”“数据工具”等宽泛概念。
- 为提高触发率罗列大量无边界关键词，导致相邻 skill 同时触发。
- 在正文重复安装、输出 envelope、典型用法、触发表和完整命令表。
- 声称“默认 JSON”，但 CLI 实际使用 `auto`；或文档字段与真实返回不符。
- 只调用实时天气，却输出未来降雨、最高温和最低温。
- 把多平台同时上榜称为事实核验，或凭平台刻板印象编造讨论角度。
- 把用户真实密码、令牌、私钥或内部文本发送给远程接口。
- 固定使用会随请求范围失效的阈值，例如不论查询几个平台都要求命中 5 个。
- 工具失败时返回空白、乱码、占位符，或用其他来源的数据冒充结果。
- 用“独有护城河”“确定能火”“绝对准确”等宣传语代替执行约束。
- 只通过 Markdown 语法校验，没有验证真实任务是否完成。

## 3. 优化前先建立事实基线

不要先改文案。按以下顺序收集事实:

1. 确认用户授权范围。仅要求分析或审查时不得修改文件；明确要求优化或修复后才落盘。
2. 列出全部 `SKILL.md`、`references/`、`scripts/`、`assets/` 和生成标记块。
3. 查找适用的 `AGENTS.md`、skill 规范、项目文档和构建约束。
4. 读取 CLI 的命令定义、参数 schema、默认输出格式、错误映射和安装流程。
5. 运行 `--help`、已有测试或只读样例，确认真实命令和字段。
6. 检查工作区状态，保留用户已有修改，不覆盖无关文件。
7. 记录以下问题，不立即润色:
   - 文档与实现冲突。
   - 触发重叠或遗漏。
   - 敏感信息和隐蔽副作用。
   - 重复内容和失效示例。
   - 不能由输入数据支持的输出结论。

事实不确定时继续查代码、测试或真实返回。不要靠记忆补全 API 行为。

## 4. 使用 TRACE 审查

### 4.1 Trust 可信任度

逐项检查:

- Skill 是否要求与任务无关的权限、安装、登录或写操作。
- 安装是否向用户说明会修改什么，并在需要时取得确认。
- 用户输入是否会离开本机；若会，是否明确禁止敏感数据。
- 命令行参数是否可能暴露在 shell 历史或进程列表中。
- 生成的密码、密钥或安全判断是否来自可信的本地机制。
- 健康、金融、法律等高风险结果是否被错误包装成确定性结论。
- 聚合、热搜或模型推断是否被误称为事实验证。
- 数据来源、时效、限流和已知不稳定接口是否透明。
- 依赖是否经过安全扫描；是否存在未知脚本、二进制、网络连接或混淆代码。
- 核心能力是否在目标网络环境中可达，是否完整支持中文输入和输出。

将安全扫描、依赖检查、国内网络连通性和中文交互测试放在发布流程中。不要把整份安全报告复制进 `SKILL.md`；只保留会改变 agent 行为的安全边界。

### 4.2 Reliability 可靠性

逐项检查:

- 命令是否真实存在，参数位置、类型、必填、枚举和默认值是否准确。
- CLI 默认格式是否为 `auto`、`json` 或 `human`；agent 是否应显式加 `--json`。
- 输入缺失时是询问用户、采用默认值还是失败；不要默默使用可能错误的默认地点或身份。
- 返回日期是否可能回退；回答是否展示实际日期。
- 空数组、`null`、部分字段缺失和部分平台失败是否有定义。
- 多步任务是否写清依赖顺序，例如先查榜单 ID，再查榜单详情。
- 多源编排是否并发执行独立请求，并在局部失败后保留可用结果。
- 输出中的每个判断是否能追溯到真实字段。
- 错误恢复是否有限且确定；不要连续猜 ID、枚举或重试网络请求。

可靠性要求“同一条件下行为一致”。不要用模糊指令“灵活处理错误”代替具体恢复动作。

### 4.3 Adaptability 适用性

`description` 是主要触发入口。使用以下结构:

```text
<核心能力>。当用户<主要意图、口语说法、缩写>时使用；<相邻能力或明确排除项>使用其他 skill / 不在范围内。
```

好例子:

```yaml
description: 查询单个平台的实时热搜。当用户指定微博、知乎、抖音等平台时使用；多平台汇总和跨平台比较使用 rxopen-trending。
```

坏例子:

```yaml
description: 热点工具。用户提到热搜、新闻、热门、趋势、舆情、内容时都使用。
```

检查三类评测语句:

1. `should-trigger`:用户明确提出核心任务。
2. `paraphrase-trigger`:用户使用口语、缩写或间接表达。
3. `should-not-trigger`:用户提出相邻 skill、普通问候或过宽表达。

不要在正文重复完整“何时用”表。触发信息应集中在 frontmatter；正文只保留触发后的路由决策。

### 4.4 Convention 规范性

采用渐进披露:

```text
skill-name/
├── SKILL.md
└── references/
    ├── install.md
    └── domain-fields.md
```

分配信息:

| 内容                           | 放置位置                            |
| ------------------------------ | ----------------------------------- |
| 名称、能力、触发和排除边界     | frontmatter `description`           |
| 核心工作流、安全边界、关键恢复 | `SKILL.md` 正文                     |
| 命令签名、参数索引             | AUTO-GEN 区块                       |
| 完整字段、枚举、复杂返回结构   | `references/`                       |
| 安装步骤等跨 skill 相同内容    | 单一模板生成到各 skill 的 reference |
| 真实测试、扫描报告、benchmark  | 测试或发布产物，不塞入 skill 正文   |

每个 skill 必须可以独立分发。不要引用 skill 目录外的共享文件，也不要依赖软链接。共享内容应在 build 时生成实体文件到每个 skill 内。

### 4.5 Effectiveness 有效性

从用户目标反推输出，而不是从命令反推输出。

| 用户目标         | 无效结果                   | 有效结果                             |
| ---------------- | -------------------------- | ------------------------------------ |
| 查看热歌榜曲目   | 只返回榜单 ID 列表         | 查到目标榜单 ID 后返回曲目           |
| 判断今天是否带伞 | 只返回当前温度             | 使用预报字段给出有依据的降水判断     |
| 对比两个平台热点 | 分别粘贴两个榜单           | 提取共同话题、独有话题和原始标题证据 |
| 查询今日新闻     | 把回退到昨天的数据称为今日 | 标注真实返回日期                     |
| 检测真实密码     | 把密码发送给远程服务       | 拒绝远程检测并给出本地安全建议       |

输出应满足:

- 回答用户问的对象、时间、范围和方向。
- 字段缺失时省略结论或明确说明，不使用占位符。
- 推理必须有字段依据，并区分事实、推断和限制。
- 内容可直接使用；不要让用户重新整理工具原始输出。
- 不为显得“有价值”而增加无关模块、追问或个性化问卷。

## 5. 重写 SKILL.md

### 5.1 查询型 Skill 模板

```markdown
---
name: example-query
description: <能力 + 主要触发 + 相邻边界>
metadata:
  requires:
    bins: ["example-cli"]
  category: data
---

# example-query

## 执行规则

1. 检查 `example-cli` 是否可用；不可用时读取 `references/install.md`。
2. 调用业务命令时显式使用结构化输出参数。
3. 写清最重要的参数陷阱、多步依赖和失败恢复。
4. 只依据返回字段回答，不编造缺失信息。

## References

- 安装与验证:`references/install.md`
- 参数和字段:`references/domain.md`

<!-- AUTO-GEN:START commands -->

...由生成器维护...
<!-- AUTO-GEN:END -->
```

### 5.2 编排型 Skill 模板

```markdown
---
name: example-workflow
description: <组合目标 + 触发条件 + 单项任务排除>
metadata:
  requires:
    bins: ["example-cli"]
  category: composite
  skillType: workflow
---

# example-workflow

## 工作流

1. 检查依赖和必要用户输入。
2. 并发执行互相独立的只读命令。
3. 依据 reference 中的真实字段合并结果。
4. 定义局部失败、全部失败和数据不足时的行为。

## 可信边界

- 写清不能证明、不能推断和不能替代的事项。

## 输出要求

- 定义结果必须包含什么，而不是固定装饰性模板。

## References

- 安装与验证:`references/install.md`
- 字段和合并规则:`references/fields.md`
```

编排型 skill 若没有自己的命令，不要为它生成整套 CLI 命令表。

## 6. 精简规则

逐段提问:“删除这段后，TRACE 的哪一项会变差？”如果答案是“都不会”，删除它。

优先删除:

- 产品宣传、价值口号和与执行无关的来源故事。
- `description`、何时用表和典型用法中的重复触发内容。
- 手写命令清单与 AUTO-GEN 命令表的重复。
- 每个 skill 都相同的完整安装步骤、输出 envelope 和通用网络错误表。
- 无法保证长期正确的静态 ID、日期、价格和返回示例。
- 为展示格式而存在的长示例对话。

必须保留:

- 触发和排除边界。
- 非显然参数、默认值陷阱和多步依赖。
- 敏感信息、写操作和远程传输限制。
- 领域特有错误恢复和部分失败策略。
- 输出正确性所需的真实字段。

不要设置死板行数。查询型 skill 通常应比编排型短；复杂度必须由必要决策数量决定，而不是模板长度决定。



## 7. 验证流程

按顺序执行，任一步失败都先修复再继续。

### 第 1 层:静态与结构校验

- 运行 skill 官方校验器。
- 检查 frontmatter、目录名和 `description` 长度。
- 检查所有 `references/*.md` 链接真实存在。
- 检查 AUTO-GEN 标记完整，且未手工篡改。
- 运行格式、lint 和 `git diff --check`。

### 第 2 层:生成、构建和代码测试

- 运行安装 reference 和命令表生成器。
- 再运行生成器的 `--check` 模式。
- 运行 typecheck 和 build。
- 运行单元测试和 CLI 端到端测试。
- 覆盖正常输入、缺失输入、边界值、空结果、远程失败和部分失败。

### 第 3 层:打包验证

- dry-run 打包。
- 确认每个独立 skill 包含 `SKILL.md` 及全部 references。
- 确认生成文件没有因 `.gitignore`、`.npmignore` 或 `files` 配置被排除。
- 从打包产物而不是源码路径做一次读取验证。

### 第 4 层:真实任务前向评测

使用接近真实用户的请求验证，不要向测试 agent 泄露预期答案。

至少覆盖:

- 典型触发请求。
- 口语化或间接触发请求。
- 相邻 skill 的不触发请求。
- 缺少 CLI 时的安装指引。
- 敏感输入拒绝或降级。
- 非显然参数。
- 多步命令串联。
- 局部数据源失败。
- 数据不足时不编造。

对每个任务记录:

- 是否触发正确 skill。
- 是否执行正确命令和参数。
- 是否遵守安全边界。
- 是否交付可直接使用的结果。
- 是否出现不必要安装、追问、重试或扩展任务。

### 第 5 层:发布环境验证

- 运行安全实验室要求的静态、依赖和动态沙箱扫描。
- 在目标国内网络环境测试核心接口、安装源和依赖下载。
- 验证中文输入、错误提示、字段解释和输出格式。
- 海外 API 无法直接使用时，提供可靠的国内可达或自部署方案；否则不得标记为国内生产可用。

## 9. 生产验收清单

### Trust

- [ ] 无未知脚本、恶意文件、越权请求或未披露网络连接。
- [ ] 敏感数据不会被发送到不可信远程服务或暴露在命令行。
- [ ] 安装、登录、写入和其他副作用已说明并在需要时确认。
- [ ] 高风险结果包含正确边界，不夸大为诊断或事实核验。
- [ ] 安全扫描、依赖扫描、国内网络和中文交互验证通过。

### Reliability

- [ ] 命令、参数、默认值、字段和日期行为与实现一致。
- [ ] 正常、边界、空结果、部分失败和全部失败均有测试。
- [ ] 多步流程、并发流程和恢复动作明确且有限。
- [ ] 生成器幂等，build 和 tests 通过。

### Adaptability

- [ ] `description` 包含能力、主要触发和相邻排除边界。
- [ ] should-trigger、口语触发和 should-not-trigger 评测通过。
- [ ] 单项查询与组合工作流不会互相误触发。

### Convention

- [ ] `SKILL.md` 只保留核心决策，详细字段放入 references。
- [ ] 机械命令表和共享安装文档由单一来源生成。
- [ ] 每个 skill 独立包含所需文件，不依赖目录外资源。
- [ ] 所有链接、frontmatter、命名、格式和打包内容通过校验。

### Effectiveness

- [ ] 真实任务输出正确、完整且可直接使用。
- [ ] 多步任务交付最终结果，而不是中间 ID 或原始数组。
- [ ] 推断有字段证据；数据不足时明确说明。
- [ ] 前向评测证明 skill 相比仅看 `--help` 提供了实际增益。

只有五组全部通过，才将 skill 标记为生产可用。

## 10. AI 执行后的交付格式

完成优化后，向用户报告:

1. 修改了哪些 skill、references、生成器和构建配置。
2. 修复了哪些 Trust、Reliability、Adaptability、Convention、Effectiveness 问题。
3. 删除了哪些重复或误导内容，以及压缩前后的规模。
4. 运行了哪些校验、构建、测试、打包和前向评测。
5. 哪些风险仍未验证，例如真实生产网络、安全实验室扫描或外部 API 稳定性。

不要只说“已优化”。给出可验证证据，并明确未完成项。
